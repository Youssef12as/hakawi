# Hakawi: improved Lightning TTS deployment

This folder contains the complete TTS service, asset preparation, container recipe, checks, and deployment steps. The commands below run in a **Lightning Studio Linux terminal**, except the explicitly marked Hakawi backend step. No backend request timeout has been changed. LitServe's existing default request timeout is also retained.

## Files

| File | Purpose |
| --- | --- |
| `server.py` | `POST /` LitServe API, prepared voice prompts, inline cloning, WAV output |
| `audio_utils.py` | Safe character names, bounded base64 input, FFmpeg decoding and conversion |
| `requirements.txt` | Exact versions for core runtime dependencies, including CUDA PyTorch |
| `setup.sh` | Existing Studio environment, dependency installation, assets, preflight, version inventory |
| `asset_versions.json` | Exact Hugging Face revisions for model and audio tokenizer |
| `voices.json` | Built-in voice URLs and reference transcripts, including Khufu and its registry alias |
| `prepare_assets.py` | Download model/tokenizer and convert built-in references to real mono WAV |
| `preflight.py` | Check CUDA, compiler, Python headers, packaged assets, and voice formats |
| `smoke_test.py` | Test health, speech, inline cloning, and the save-character action |
| `Dockerfile` / `.dockerignore` | Optional reproducible container build with prepared assets |
| `tests/test_server.py` | CPU checks for real audio conversion and API behavior using a fake model |

`models/`, `pre_existing_voices/`, and `installed-versions.txt` are generated by setup. Model weights are not included in the downloadable source ZIP. The first setup downloads several gigabytes; allow adequate disk space. Keep the generated version inventory with your release after the GPU test passes. It records the managed Studio environment and must not be used as a portable Docker lock file.

## 1. Upload the files into the Studio

Use a new folder so your working server remains available for rollback:

```bash
mkdir -p /teamspace/studios/this_studio/hakawi-tts
cd /teamspace/studios/this_studio/hakawi-tts
```

Upload the supplied source files into this folder using the Studio file browser. Preserve the `tests/` subfolder and the hidden `.dockerignore` / `.gitignore` files. If uploading the ZIP, extract its contents directly into `hakawi-tts`; `server.py` should be directly inside that folder.

Select a **T4 GPU** for the Studio while testing. CPU is sufficient for downloads, but setup's preflight and the server require CUDA.

## 2. Install system tools and prepare the service

```bash
sudo apt-get update
sudo apt-get install -y ffmpeg libsndfile1 gcc
bash setup.sh
```

`setup.sh` uses the Studio's existing managed conda environment, installs the pinned packages, downloads both the TTS model and its audio tokenizer, converts the built-in recordings, and checks the GPU. Do not create another virtual environment: this Studio permits only its default conda environment. The reported Python 3.12 environment is suitable. It stops on any failure; resolve the reported error before continuing. It does not start or deploy a paid cloud service.

For this setup, the pinned PyTorch build is **2.8.0 with CUDA 12.8**. If CUDA preflight fails, check the Studio's NVIDIA driver and CUDA compatibility before deployment. NVIDIA environment variables alone cannot provision a GPU or repair incompatible drivers. `preflight.py` actually executes a CUDA operation.

If Python headers are reported missing, inspect the exact interpreter's include directory:

```bash
python -c "import sysconfig; print(sysconfig.get_path('include'))"
```

Install development headers matching that interpreter, rather than an unrelated system Python version. Check the managed conda interpreter for its own headers; the official Python container also supplies its own matching headers.

If a voice download fails, correct its URL in `voices.json` and rerun:

```bash
python prepare_assets.py --voices-only
python preflight.py
```

Use a transcript that matches the recording exactly. Prefer clear 3–10 second clips. The service accepts 0.5–30 seconds to remain compatible with longer existing references; it rejects oversized or silent clips rather than trimming them against an unchanged transcript.

## 3. Test on the Studio GPU

In the first terminal:

```bash
cd /teamspace/studios/this_studio/hakawi-tts
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 VOICE_CACHE_DIR=/tmp/hakawi-tts-studio-test-voices python server.py
```

Wait for the `Ready:` log. Startup includes model loading, reference encoding, and one warmup generation. Warmup reduces first-request overhead; it does not guarantee a particular response time or eliminate future restarts.

In a second terminal:

```bash
cd /teamspace/studios/this_studio/hakawi-tts
python smoke_test.py
python smoke_test.py --character khufu --output test-output/khufu.wav
python -m unittest discover -s tests -v
```

Listen to the generated WAV files in the Studio file browser. Passing audio-format checks alone does not establish voice quality.

Optional test of the save-character action:

```bash
python smoke_test.py \
  --character studio-test \
  --save-only \
  --inline-audio pre_existing_voices/am-othman.wav \
  --ref-text "$(cat pre_existing_voices/am-othman.txt)"
python smoke_test.py --character studio-test --output test-output/studio-test.wav
```

Stop the local server with Ctrl+C when finished. Its test voices were written under `/tmp`, rather than into the source folder.

## 4. Create the cloud deployment from the tested Studio

The simplest route is a **Studio snapshot deployment**. Lightning documents this as an independent deployment created from the Studio environment; it does not require publishing a Docker image. This replaces the old guide's version-dependent `lightning api deploy server.py --cloud` command.

Install the deployment CLI in the existing Studio environment:

```bash
python -m pip install "lightning-sdk==2026.10.1"
lightning login
lightning api /v1/memberships
```

Run `python -c "import sys; print(sys.executable)"` and use that interpreter path in the startup command below; `/home/zeus/miniconda3/envs/cloudspace/bin/python` matches the environment reported in this Studio. Also replace the application folder with the actual absolute folder shown by `pwd` if you uploaded into another location. Find the actual owner/teamspace and Studio names in your account. Replace the following placeholders; do not run them literally:

```bash
export HAKAWI_TEAMSPACE="YOUR_OWNER/YOUR_TEAMSPACE"
export HAKAWI_STUDIO="YOUR_STUDIO_NAME"
export HAKAWI_DEPLOYMENT="hakawi-tts-v2"
```

Create a separate deployment for this release so the old endpoint remains available until the new one passes testing:

```bash
lightning deployment create "$HAKAWI_DEPLOYMENT" \
  --teamspace "$HAKAWI_TEAMSPACE" \
  --studio "$HAKAWI_STUDIO" \
  --command "/home/zeus/miniconda3/envs/cloudspace/bin/python /teamspace/studios/this_studio/hakawi-tts/server.py" \
  --machine T4 \
  --cloud gcp-lightning-public-prod \
  --port 8000 \
  --min-replicas 1 \
  --max-replicas 1 \
  --autoscale-metric GPU \
  --autoscale-threshold 80 \
  --api-key-auth \
  -e HF_HUB_OFFLINE=1 \
  -e TRANSFORMERS_OFFLINE=1 \
  -e TOKENIZERS_PARALLELISM=false \
  -e VOICE_CACHE_DIR=/tmp/hakawi-tts-voices
```

The command creates a running GPU deployment. Minimum 1 keeps compute allocated during verification; change it to 0 after testing. `gcp-lightning-public-prod` is the Lightning-managed GCP account identifier used by the current CLI. If your team uses another connected GCP account, substitute that account's identifier shown in your deployment settings. Leave interruptible/spot disabled for the demo.

Check progress and retrieve the endpoint:

```bash
lightning deployment inspect "$HAKAWI_DEPLOYMENT" --teamspace "$HAKAWI_TEAMSPACE"
lightning deployment logs "$HAKAWI_DEPLOYMENT" --teamspace "$HAKAWI_TEAMSPACE" --tail 100
```

In the Lightning dashboard, check:

| Setting | Initial value |
| --- | --- |
| Machine | 1 × T4 |
| Exposed port | 8000 |
| Authentication | User API key / Bearer |
| Interruptible | Disabled |
| Minimum / maximum replicas during verification | 1 / 1 |
| Autoscaling metric | GPU, initial threshold 80% |
| Idle timeout after switching minimum to 0 | 300 seconds |
| Health check, where configurable | `/health`, port 8000 |

The CLI exposes GPU, CPU, and RPM metrics. The 80% GPU threshold is a starting setting to measure, not a throughput guarantee; with maximum 1 it cannot add another machine. Permit enough startup time for model loading and warmup if the dashboard exposes a startup-grace setting.

UI alternative: install/open the Studio's Deployment plugin, choose **New Deployment → Studio**, enter the same absolute command and port, choose T4 and Bearer authentication, and apply the table above. See [Lightning's Studio deployment instructions](https://api.lightning.ai/docs/platform/build/ai-studio/deploy-a-studio).

## 5. Test the secured cloud endpoint

Copy the new URL from the deployment inspection or dashboard. Use your Lightning API key from API playground/account settings. Enter it privately instead of putting it into a command or source file:

```bash
export VOICE_API_URL="https://YOUR_NEW_DEPLOYMENT_ENDPOINT"
read -r -s -p "Lightning Bearer API key: " VOICE_API_KEY
printf '\n'
export VOICE_API_KEY
python smoke_test.py --output test-output/cloud-othman.wav
python smoke_test.py --character khufu --output test-output/cloud-khufu.wav
```

Test a voice that is not built into the deployment:

```bash
python smoke_test.py \
  --character deployment-test \
  --inline-audio pre_existing_voices/am-othman.wav \
  --ref-text "$(cat pre_existing_voices/am-othman.txt)" \
  --output test-output/cloud-custom.wav
python smoke_test.py --character deployment-test --output test-output/cloud-custom-cached.wav
```

The first custom request creates its prepared prompt; the second should reuse it. Confirm that a request without the Bearer key gets rejected by the Lightning gateway. Do not disable gateway authentication: the server relies on it for cloud access control.

## 6. Connect Hakawi's backend

On your **Hakawi backend machine**, edit only these entries in `backend/.env`, preserving the other settings:

```dotenv
VOICE_API_URL="https://YOUR_NEW_DEPLOYMENT_ENDPOINT"
VOICE_API_KEY="YOUR_LIGHTNING_BEARER_API_KEY"
```

If the backend is hosted on Azure or Render, set the same values in that service's environment settings. Do not rely on the old Studio URL still present as the source-code default.

Restart the backend. For the local Windows project, from an activated backend environment:

```powershell
Set-Location -LiteralPath 'E:\CU NEXUS HACATHON\Hakawi\backend'
python -m uvicorn src.main:app --host 0.0.0.0 --port 8000 --reload
```

Verify regional chat, Ramsis in both language modes, Khufu, and a saved family member. Text chat and speech remain separate requests: the frontend receives chat text, then calls `/api/tts` for audio. No application API changes or timeout edits are needed.

## 7. Enable scale-to-zero and test recovery

Return to the Studio terminal:

```bash
lightning deployment update "$HAKAWI_DEPLOYMENT" --teamspace "$HAKAWI_TEAMSPACE" --min-replicas 0 --max-replicas 1
```

Set the dashboard idle timeout to 300 seconds. Allow the deployment to become idle and reach 0 replicas; avoid test calls or keep-alive pings during this interval. Then send a new request through Hakawi.

Custom audio files and prompts are **local replica caches**. They can disappear after scale-to-zero, a restart, or a new release, and are not shared between replicas. Supabase remains the durable source of user voices. Hakawi already retries a `not found` voice with inline audio/reference text, so test that a saved family member still speaks after the deployment wakes. A direct request for `deployment-test` without inline audio may report `not found` after a fresh replica; resend the inline test command above to restore it. This is expected.

Sleep the Studio, then test Hakawi again. The cloud deployment should remain independent of the sleeping Studio. The current timeout behavior can still produce slow or failed requests during cold starts; timeout changes were deliberately deferred.

## 8. Demo settings and later updates

Before the demo:

```bash
lightning deployment update "$HAKAWI_DEPLOYMENT" --teamspace "$HAKAWI_TEAMSPACE" --min-replicas 1 --max-replicas 1
python smoke_test.py --output test-output/demo-check.wav
```

After the demo:

```bash
lightning deployment update "$HAKAWI_DEPLOYMENT" --teamspace "$HAKAWI_TEAMSPACE" --min-replicas 0 --max-replicas 1
```

Keep maximum 1 until concurrent testing shows a need for more. Then allow up to 3 and measure queueing, response times, GPU load, and cost. Each replica has one model worker and its own voice cache. Batching remains disabled.

For later source updates: edit the Studio files, run preflight and the GPU smoke tests, then use the existing deployment's **Update** button in the Deployment plugin to capture a new Studio snapshot. An ordinary scaling update does not capture changed source. Keep the previous release available under **Releases** for rollback. Retain the old backend URL securely until the new endpoint has passed the application tests.

## Optional: deploy the same files as a Docker image

The Studio snapshot path above does not use `Dockerfile`. If you choose a container deployment instead, run setup first so model assets and converted voices exist. Then, on a Linux machine with Docker:

```bash
docker build --platform linux/amd64 -t hakawi-tts:v2 .
docker run --rm --gpus all -p 8000:8000 hakawi-tts:v2
```

Run the smoke tests from another terminal. To deploy this container, push a versioned image to your team's registry and select it as the Docker image source in Lightning. For example, after replacing the registry placeholder:

```bash
export HAKAWI_IMAGE="YOUR_REGISTRY/YOUR_NAMESPACE/hakawi-tts:v2"
docker tag hakawi-tts:v2 "$HAKAWI_IMAGE"
docker login YOUR_REGISTRY
docker push "$HAKAWI_IMAGE"
```

For private images, configure registry credentials in Lightning before deploying. Expose port 8000, use the same T4/auth/scaling settings, and use the image's default startup command. Prefer an immutable image digest for releases. See [Lightning container deployment documentation](https://lightning.ai/docs/overview/deploy-containers).

## Improvements in this version

- Paths are relative to `server.py`, working in both the Studio and `/app` containers.
- The main model **and the separate audio tokenizer** are packaged at fixed revisions, enabling offline runtime loading.
- References are encoded into reusable voice prompts; generation reuses those prompts instead of repeatedly processing reference files.
- The prompt cache is bounded to 128 voices and stores reference tokens on CPU, limiting persistent GPU-memory use.
- WAV, MP3, and browser WebM recordings are decoded by content and converted into actual mono WAV files.
- Names, base64, text length, file size, audio duration, and silence are checked before cloning.
- Content-addressed reference files and atomic manifests keep successful custom-voice updates consistent.
- WAV output uses the model's sample rate.
- One inference worker, startup warmup, readiness checks, and per-generation timings make operation easier to diagnose.
- Core packages and model revisions are pinned; setup records installed versions for auditing. Docker installs the pinned requirements directly and resolves remaining dependencies during its build.
- Existing `generate`, `save_character`, `audio_base64`, and `not found` behavior remain compatible with Hakawi.
- Backend and LitServe request timeout policies remain unchanged.

Prepared prompt reuse follows [OmniVoice's supported API](https://github.com/k2-fsa/OmniVoice#reusing-a-cloned-voice-across-sessions). Model placement and sample-rate handling are also illustrated in the [Lahgtna author's demo](https://huggingface.co/spaces/oddadmix/Lahgtna-OmniVoice-Demo/blob/main/app.py).
